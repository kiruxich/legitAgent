# legitAgent — спецификация v1

Дата: 2026-08-13  
Статус: согласовано в брейнсторме, ждёт ревью перед планом реализации

Это не юридический сервис и не замена юристу. legitAgent ищет в коде типичные риски по 152-ФЗ и показывает, на какую статью они похожи. Решение «нарушаете вы закон или нет» принимает человек.

Что отложили на потом — в [файле бэклога](./2026-08-13-legitagent-backlog.md).

---

## Зачем это

Разработчик сайта в РФ часто узнаёт про 152-ФЗ после деплоя или после претензии. Нужна проверка **до коммита**: в Cursor и в терминале, по исходникам.

Первая версия отвечает на вопрос: «в этом React/Next или HTML-проекте есть три грубых дыры по персональным данным?» и умеет **объяснить остальные пункты чек-листа**, даже если ещё не умеет их найти в коде.

## Что входит в v1

- Имя продукта: **legitAgent**
- Монорепозиторий на TypeScript, pnpm workspaces (без Turborepo)
- Три пакета в npm-организации `@legitagent`
- Каталог всех известных нам веб-проверок по 152-ФЗ
- Автопоиск только трёх нарушений (см. ниже)
- Короткие выдержки нужных статей закона в репозитории
- CLI и MCP на одном движке
- Тесты на фикстурах
- README, дисклеймер, MIT
- Логотип SVG в репозитории
- Публичный GitHub-репозиторий и публикация пакетов в npm

## Что не входит в v1

Playwright, GitHub Action, Vue/Svelte, полный корпус законов, 38-ФЗ/ERID, ЗоЗПП, английский язык вывода, файл конфига проекта. Полный список — в бэклоге.

## Три части продукта

Представь сантехника с одним чек-листом и двумя способами вызвать: по телефону и в мессенджере. Чек-лист один.

1. **Мозг — `@legitagent/core`**  
   Читает файлы проекта, сверяет с правилами, возвращает список находок. Сам по себе «кнопок» не имеет.

2. **Терминал — `@legitagent/cli`**  
   Команда: `npx @legitagent/cli scan [путь]`. Печатает список по-русски. Если есть серьёзные находки (`high`) — код выхода `1`. Флаг `--json` — тот же список машине.

3. **Cursor — `@legitagent/mcp`**  
   В `.cursor/mcp.json`: `"command": "npx", "args": ["-y", "@legitagent/mcp"]`.  
   Три инструмента:
   - `scan` — проверить проект (как CLI)
   - `list_rules` — показать весь каталог, включая то, что ещё не ищем в коде
   - `explain_rule` — зачем правило, выдержка из статьи, как чинить  

   MCP **не пишет патчи**. Cursor может предложить правку сам, получив список.

Новое правило добавляется в каталог. Если для него написан искатель — `scan` его подхватывает. Если нет — правило всё равно видно в `list_rules` и `explain_rule`.

## Как хранятся правила и закон

Это не база «всех законов РФ». Два разных хранилища в `core`:

**Каталог правил** (`rules/*.yaml`) — наш чек-лист. Каждая запись:

| Поле | Смысл |
|---|---|
| `id` | Латиницей, стабильный, например `PDN.FORM.NO_CONSENT` |
| `law` | Какой закон и статья, например `152-ФЗ ст. 9` |
| `severity` | `high` / `medium` / `low` |
| `status` | `active` — ищем в коде; `planned` — только объясняем |
| `title`, `message`, `fix` | По-русски: название, что не так, как исправить |
| `excerptRef` | Ключ к выдержке статьи |

**Выдержки закона** (`legal/*.yaml`) — короткие фрагменты **только тех статей, на которые ссылаются правила**. Полный 152-ФЗ не кладём. Обновление текстов — руками, когда меняется закон.

Правило без выдержки публиковать нельзя: у каждой `active` и `planned` записи должен быть `excerptRef`.

Откуда берём чек-лист: публичные методики проверки сайтов по 152-ФЗ (политика, формы, cookie/метрики, трекеры, локализация, уведомление РКН). Не копируем закрытые движки вроде SitePravo.

## Какие правила в каталоге v1

В каталог кладём таксономию целиком (чтобы было видно «все правила, которые мы знаем для сайта»). Точные формулировки `message`/`fix` пишутся при реализации, смысл такой:

**Политика ПДн**

- Есть ли в проекте ссылка на политику (`privacy`, `политика`, `/personal-data` и похожие) — **active**
- Политика доступна, в ней оператор, цели, сроки, отзыв согласия — `planned` (в v1 по исходникам надёжно не проверить)

**Формы и согласие**

- Форма с полями ФИО / email / телефон без чекбокса согласия — **active**
- Чекбокс согласия предзаполнен — `planned`
- Нет ссылки на политику рядом с согласием — `planned`

**Метрики и cookie**

- Яндекс.Метрика / Google Analytics / gtag / Facebook Pixel / VK Pixel инициализируются сразу, без обёртки согласия — **active**
- Cookie пишутся до согласия — `planned` (нужен живой браузер)
- Баннер с возможностью отказа — `planned`

**Прочее (всё `planned`)**

- Иностранные трекеры / трансграничная передача
- Локализация ПДн (сервер не в РФ) — без пост-деплоя не видно
- Уведомление в РКН, ответственный за ПДн — в коде сайта обычно не видно; MCP только объясняет норму

Итого **три active-детектора** с фиксированными id:

| id | Что находит |
|---|---|
| `PDN.FORM.NO_CONSENT` | Форма с ПДн-полями без чекбокса согласия |
| `PDN.TRACKER.NO_CONSENT` | Метрика/пиксель без обёртки согласия |
| `PDN.POLICY.NO_LINK` | В проекте нет ссылки на политику ПДн |

Остальное в каталоге с `status: planned`.

### Как три детектора смотрят на код

Сканируем только `.html`, `.jsx`, `.tsx`. Пропускаем `node_modules`, `.next`, `dist`, `build`, `coverage`, `.git`.

1. **Форма без согласия.** Есть `<form>` или похожий JSX-компонент формы, внутри поля ввода email/tel/name/phone/fio, и нет checkbox/согласия (текст про «обработку персональных данных» / `consent`). Не гоняемся за всеми кастомными UI-китами в v1: ищем обычные `form`, `input`, `checkbox`. Сомнение → лучше находка, чем пропуск (ложное срабатывание можно заглушить позже конфигом — конфиг в бэклоге).

2. **Метрика без согласия.** В файле есть вызовы вроде `ym(`, `gtag(`, `ga(`, `fbq(`, `VK.Retargeting` на верхнем уровне модуля или в `useEffect` без условия согласия. Не считаем «согласие найдено», если в проекте просто есть слово cookie в README.

3. **Нет ссылки на политику.** По всему проекту (те же расширения) нет `href`/ссылки, похожей на политику. Один раз на проект, не на каждый файл.

HTML разбираем через parse5. JSX/TSX — через ts-morph.

## Как проходит проверка

1. Пользователь запускает `scan` (CLI или MCP). Корень — переданный путь или текущая папка.
2. Собираются файлы по glob.
3. Каждый файл отдаётся парсеру. Если файл сломан — предупреждение, файл пропускаем, остальные идут дальше.
4. Запускаются только правила со `status: active`.
5. Находка всегда содержит: `ruleId`, файл, строка (если есть), severity, русский `message`, `fix`, цитата статьи.
6. Если подходящих файлов нет — сообщение «нечего сканировать», это не авария (код выхода `0`).
7. Если есть хотя бы одна находка `high` — CLI код выхода `1`.

Zero-config: в v1 нет `legitagent.config.json`.

## Ошибки и тонкости

- Битый YAML правила — ошибка при старте с именем файла, сканер не «тихо пустой».
- Битый исходник сайта — skip + warning.
- MCP без папки проекта — явная ошибка «укажите корень».
- В CLI, MCP `explain_rule` и README одна мысль: эвристики, не юрзаключение.
- Пакеты scoped: публиковать только с `npm publish --access public`.

## Тесты

Маленькие папки-фикстуры в репозитории, не живые сайты.

- Плохая форма → находка `PDN.FORM.NO_CONSENT`
- Форма с чекбоксом согласия → этой находки нет
- `ym(...)` в корне модуля → находка по метрике
- Ссылка на `/privacy` в вёрстке → нет находки «политика отсутствует»; без ссылки — есть
- `list_rules` возвращает и `active`, и `planned`
- CLI `--json` парсится и содержит те же `ruleId`

Перед публикацией в npm эти тесты должны проходить.

## Успех v1

Можно сказать «готово», если:

1. `npx @legitagent/cli scan` на фикстурах находит три класса нарушений и не орёт на чистую форму.
2. В Cursor после трёх строк в `mcp.json` агент умеет просканировать проект и объяснить правило из каталога.
3. В каталоге есть таксономия (не только три правила), у каждого правила — статья и выдержка.
4. Репозиторий на GitHub, пакеты в npm, логотип в README, дисклеймер на месте.
5. Тесты зелёные.
